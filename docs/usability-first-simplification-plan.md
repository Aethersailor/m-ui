# m-ui 易用性优先的全面简化方案

## 1. 目标

m-ui 的目标用户是管理一台服务器上一个 Mihomo 实例的个人管理员。项目不应要求
用户理解 bootstrap capability、回环来源判断、Controller connect/bind、CORS、
pending generation、Revision SHA、degraded 状态机或服务重启顺序，才能完成正常使用。

完成本方案后，两种部署方式都必须满足同一条主路径：

1. 执行一条安装命令；
2. 打开安装器输出的面板链接；
3. 在网页创建管理员；
4. 通过向导创建第一个 Listener 和用户；
5. 页面直接显示可复制链接和二维码，并确认 Mihomo 已经加载该配置。

正常路径不要求 SSH 隧道、手工编辑 TOML、进入容器执行命令、理解内部端点、手工生成
REALITY 密钥、先创建再启用、手工重启两个服务或查看配置 Revision。

## 2. 判断“安全”还是“过度设计”的标准

保留不会增加正常操作步骤、并且直接防止凭据泄露、无效配置或服务中断的机制：

- Argon2id 密码哈希；
- Session Cookie、同源检查和登录限速；
- 数据库中敏感字段加密；
- 高熵、一次性首次设置能力；
- `mihomo -t` 候选配置校验；
- 同文件系统原子替换、最后可用配置和自动回退；
- m-ui 与 Mihomo 的长期非 root 运行；
- Controller 默认仅回环访问且带认证。

删除或降级任何要求用户为内部实现承担认知成本，但没有建立新的有效授权边界的机制：

- setup token 已经有效时仍强制客户端、Host 和 Origin 都是 loopback；
- 无条件拒绝反向代理头；
- 普通登录允许远程 HTTP，首次设置却单独禁止远程 HTTP；
- 把内部状态机名、哈希、generation 和重启顺序直接暴露给普通用户；
- 将一次业务操作拆成多次发布和多次确认；
- 发生可恢复错误后永久阻止所有配置写入；
- 为不需要后台工作的功能增加常驻 scheduler、重复数据库状态机和默认 UI。

## 3. 当前已确认的问题

### 3.1 首次设置链路自相矛盾

- 默认面板监听 `0.0.0.0:2095`，README 要求直接访问服务器 IP；
- `setupTransportAllowed` 却只允许 loopback peer、loopback Host、loopback Origin，并拒绝
  所有 Forwarded 头；
- README 建议替换 setup link 主机名，但替换后的请求必然被后端拒绝；
- Docker smoke 只通过 `127.0.0.1` 测试，因此没有覆盖文档承诺的真实用户路径；
- 没有 token 时仍展示不可提交的完整表单，只给出要求用户另开终端和 SSH 隧道的错误。

### 3.2 第一个可用节点需要过多操作

当前流程是：创建禁用的 Listener、进入详情、生成或补齐 REALITY 参数、创建用户、启用
Listener、再打开分享弹窗。每一步都要求用户理解实现概念，并可能触发独立配置发布。

### 3.3 设置页把实现细节当成产品能力

普通设置页暴露 Panel bind、Controller bind、Controller connect、CORS、pending 状态以及
m-ui/Mihomo 重启顺序。用户的真实目标只是“面板从哪里访问”和“节点能否正常工作”。

### 3.4 故障模型面向开发者而不是管理员

当前 UI 使用 `degraded`、Revision、SHA、pending、rolled_back 等术语。可自动恢复的故障
不应转化成全局永久写入锁；不可自动恢复时也应提供“重试应用”“恢复上一个可用配置”
和可复制诊断，而不是只要求人工理解状态机。

### 3.5 部署仍有不必要的手工作业

原生安装已经接近一条命令，但输出的链接与后端限制冲突。Docker 仍要求手工创建目录、
设置 UID/GID、下载 Compose、启动容器，再进入容器获取 setup link。

### 3.6 项目体量与产品范围不匹配

当前 `internal/` 约有 18,000 行生产 Go 代码和 11,000 行测试。对于单机、单管理员、
单协议族产品，核心管理、发布协调、持久化状态机和 HTTP 适配层的总复杂度已经明显影响
迭代速度和用户体验。简化必须以删除状态和分支为目标，而不只是重新包装 UI。

## 4. 目标首次使用体验

### 4.1 安装完成页

安装器只输出：

- 安装成功；
- 面板 URL；
- 下一步“打开链接完成设置”；
- 失败时才输出诊断命令。

原生安装器和 Docker 安装器都在当前交互终端直接打印完整 setup URL。setup capability
不得写入持久日志。Docker 手工部署仍保留查询命令作为备用路径。

### 4.2 管理员设置页

- 有有效 token：直接显示管理员表单；
- 没有 token：不显示灰掉的密码表单，改为显示准确的本机/Docker 查询命令，并提供
  “粘贴设置码”输入框；
- 接受服务器 IP、域名、HTTPS 反向代理或 SSH 隧道访问；
- 只以高熵 token 和同源请求作为首次设置授权，不以网络来源作为额外授权；
- token 使用后立即失效，地址栏 fragment 仍在前端启动时清除；
- 用户名默认 `admin`，允许直接使用；密码规则只限制合理最小长度和最大字节数，不增加
  大小写、数字、符号等组合规则；
- 成功后自动登录并进入首次使用向导。

### 4.3 首次使用向导

向导只询问用户不能可靠推导的内容：

1. 对外访问地址：默认从浏览器当前 hostname 推导，可修改；
2. Listener 名称：默认“默认节点”；
3. 监听端口：默认 `443`；
4. REALITY Server Name 和目标地址；
5. 第一个用户名称和可选到期时间。

以下内容自动完成：

- 监听地址使用 `0.0.0.0`；
- 生成 REALITY 公私钥与 Short ID；
- 生成用户 UUID；
- 创建 Listener 与用户；
- 编译并校验一次候选 YAML；
- 发布并加载一次；
- 确认 Mihomo 进程、Controller 和 Listener 状态；
- 显示 VLESS 链接、二维码和客户端 YAML。

整个向导使用一个后端业务操作。任何失败都不能留下“Listener 已创建但没有用户”或
“用户已创建但 Listener 仍禁用”的半成品。

### 4.4 首次进入 Dashboard

Dashboard 首屏优先展示：

- “节点已就绪”或一条明确的修复动作；
- 节点地址与端口；
- 用户数量；
- 复制链接和二维码入口；
- 当前流量、连接和核心版本。

Revision 编号、SHA、内部观察时间和实现状态移动到高级诊断页。

## 5. 后端简化设计

### 5.1 首次管理员

保留现有随机 token、哈希校验、加密存储和一次性消费，删除
`setupTransportAllowed` 的 loopback/Forwarded 限制。POST 只需满足：

- 单个合法 setup token；
- `Origin` 与请求 Host 同源；
- bootstrap 尚未完成；
- 用户名和密码合法；
- 速率限制未触发。

将 `setup-link` 和 `rotate-setup-token` 合并为：

```text
m-ui admin setup-link [--rotate] [--base-url URL]
```

CLI 默认从配置生成可访问 URL；安装器传入探测到的 URL。密码恢复默认使用交互式 TTY
两次输入，`--password-file` 仅作为自动化兼容选项。

### 5.2 一次性 onboarding 业务操作

增加一个明确的 `CompleteOnboarding` service 方法和一个 API。它在一次发布操作中创建
Listener、REALITY 密钥、首位 Listener 用户并启用 Listener。已有用户仍可使用当前细粒度
API 日常管理。

### 5.3 配置发布状态机

保留“数据库是期望状态、YAML 是构建产物”，但把失败模型收敛为两个 generation：

- `desired_generation`：数据库中最新期望状态；
- `applied_generation`：Mihomo 当前确认加载的状态。

新流程：

1. 根据候选业务状态生成 YAML；
2. 运行真实 `mihomo -t`，失败则完全不写数据库；
3. 提交期望状态和新的 desired generation；
4. 原子发布、reload 并健康检查；
5. 成功后更新 applied generation；
6. 运行时失败则恢复最后可用 YAML，保留“待重试”状态和脱敏错误。

启动时自动重试 `desired != applied`，失败也必须让管理面板启动。删除全局永久
`degraded` 写入锁；用户可以修正期望状态、重试应用或恢复最后可用版本。

Revision 只保存成功应用的结构化快照。失败进入操作日志，不创建 failed Revision；回滚是
把一个旧成功快照作为新的 desired generation 重新验证和发布，不再维护
pending/failed/rolled_back 多状态历史。

### 5.4 端点设置

普通设置只保留：

- 面板访问地址；
- 分享链接使用的公网地址；
- 语言和主题；
- HTTPS Cookie 开关或自动探测结果。

Controller bind/connect/CORS 放入“高级设置”，默认折叠并附带用途说明。保存后由后端计算
需要应用的动作，UI 只显示一个“应用并重启”按钮；不要求用户手工判断重启顺序。

评估删除 `endpoint_settings_pending` 与 `endpoint_settings_last_applied` 两张专用表，统一并入
desired/applied generation。不得继续存在两套相互独立的 pending 状态机。

### 5.5 Mihomo 核心管理

核心通道与自动更新是明确的产品能力，必须保留 `release` 和 `alpha`，并把用户选择作为
持久化策略，而不是当前进程或当前 m-ui 版本的一次性选项。系统设置中的“核心”卡片保留：

- 通道：`release` 或 `alpha`；
- 自动更新开关；
- 检查周期；
- 当前核心、所选通道最新核心、最后检查与最后更新结果；
- 立即检查、立即更新和回退到上一个已验证核心。

设置写入 SQLite。加载优先级必须是：已有数据库中的用户设置最高；安装包、镜像、TOML 和
程序默认值只在数据库尚无核心设置时用于初始化。更新、重装或容器重建 m-ui 都不得覆盖
已经保存的通道、自动更新开关和检查周期。

m-ui Release 内置的已验证 Mihomo 只承担全新安装 bootstrap、当前核心丢失时的恢复以及
离线兜底，不代表用户之后必须跟随 Release 通道。若用户选择“`alpha` + 自动更新”，语义是
“始终对齐官方 Alpha 通道的最新已验证身份”：

1. m-ui 启动并恢复管理面板；
2. 读取 SQLite 中保存的核心策略；
3. 自动更新开启时，每次 m-ui 启动都立即在后台检查所选通道的最新官方身份；检查完成后
   继续遵守用户保存的检查周期；
4. 当前核心不是该通道最新身份时，下载候选、校验资产身份和摘要；
5. 使用当前配置执行真实 `mihomo -t`；
6. 原子切换核心、重启并健康检查；
7. 成功后记录当前身份和最后更新时间。

“最新”按所选通道的官方发布身份、发布时间和目标 commit 判断，不能用 Release 与 Alpha
之间不可比较的版本字符串决定，也不能因为 m-ui 更新时附带了另一个通道的核心就重置用户
选择。用户切换通道并保存后，应立即触发一次后台对齐；关闭自动更新时只保存通道并允许
手工检查/更新。

为保证“更新 m-ui 后仍自动使用最新 Alpha”，启动调度不依赖当前 m-ui 版本，也不再增加一份
“上次启动版本”状态。只要数据库中的自动更新已开启，启动就把一次后台检查排到当前时间；
成功或失败后重新按用户保存的检查周期调度。这样升级、重装、容器重建和普通重启只有一条
完全相同、可预测的恢复路径。

后台更新不得阻塞面板启动。下载、验证、重启或健康检查失败时继续运行最后一个健康核心，
保留用户设置，记录脱敏错误并按检查周期重试；核心更新失败不得触发全局 degraded 写入锁。
只保留一个更新协调器、一份持久化策略和最近一个健康备份，删除与这些语义无关的重复状态
和并发分支，而不是删除 Alpha 或自动更新本身。

### 5.6 认证与浏览器安全

保留 Session Cookie、Argon2id、登录限速以及浏览器 mutation 的同源保护。CSRF 实现是否
保留独立数据库 token，在重构时以“能否显著减少状态和分支”为准；这类机制不能增加任何
用户步骤。

远程 HTTP 的处理必须一致：要么整个面板允许并显示醒目风险提示，要么整个面板要求 HTTPS；
不能只禁止首次设置而允许之后的登录密码和 Session 继续走 HTTP。当前产品选择为允许直接
访问，因此 v0.2 先采用“允许并警告”，不再硬阻断首次设置。

## 6. 前端信息架构

主导航收敛为：

- 概览；
- 节点；
- 系统。

“配置”页并入系统的高级诊断区域。普通节点列表提供创建、启停、用户和分享；REALITY
私钥、Short ID、YAML、Revision 和审计仅在明确展开高级信息时出现。

所有错误必须包含：

- 发生了什么；
- 当前服务是否仍可用；
- 推荐的下一步按钮；
- 可展开复制的技术详情。

不再把后端错误码或英文状态枚举直接展示为主要文案。

## 7. 部署简化

### 7.1 原生部署

保留现有一行安装命令。安装脚本负责：安装、启动、健康检查、生成 setup URL，并在最后
只打印面板链接。若自动探测地址失败，输出相对路径和明确的替换提示，不生成一个看似可用
但会被后端拒绝的链接。

### 7.2 Docker 部署

增加官方 `install-docker.sh`，一条命令完成：

- 创建 `/opt/m-ui/data`；
- 设置 `10001:10001` 和所需权限；
- 下载单服务、单挂载、`latest` Compose；
- 启动并等待健康；
- 在当前终端打印完整 setup URL。

Compose 继续保持一个长期服务和一个数据挂载。初始化脚本可以使用 root 完成宿主目录准备，
长期容器仍以 UID/GID `10001:10001` 运行。不得为了“纯 Compose”美观把权限准备重新转嫁给
普通用户。

### 7.3 升级和恢复

用户级命令只保留：

- 安装/更新；
- 状态；
- 诊断；
- 备份/恢复说明；
- 交互式管理员密码恢复。

`core bootstrap`、runtime finalize、apply-mihomo-start 等内部命令从顶层帮助中隐藏到
`m-ui internal`，避免把部署实现当成用户 API。

## 8. 兼容与迁移

- 已有管理员、Session、Listener、用户、密钥和分享链接不得改变；
- 已消费的旧 bootstrap 不得重新开放；未完成 bootstrap 可继续使用原 token；
- 原 endpoint pending 状态迁移到统一 desired/applied generation；
- 只迁移成功 Revision，失败记录保留为只读审计或在备份后清理；
- 当前受管核心继续运行；现有 `release`/`alpha`、自动更新和检查周期设置原样迁移，升级、
  重装及容器重建不得改写；
- 升级前创建 SQLite、master key、YAML、Revision 和 core manifest 的一致性备份；
- 任意迁移失败必须继续运行旧版本，不得留下新旧程序同时写同一数据目录。

## 9. 实施阶段

### Phase 1：修通首次设置（补丁版本）

- 删除 loopback-only setup transport；
- 修正 setup page 的无 token 状态；
- 合并 setup CLI；
- 修正文档；
- 增加真实非回环 Host、反向代理和 token replay 测试。

验收：从另一台机器通过服务器 IP 打开安装器输出链接，能够创建管理员并自动登录。

### Phase 2：首次使用向导

- 增加原子 onboarding API；
- 实现三步以内的 Web 向导；
- 自动生成密钥、UUID、发布并显示分享信息；
- Dashboard 增加就绪状态和分享入口。

验收：全新部署从打开链接到取得可导入客户端的二维码不超过三分钟，无需打开高级设置。

### Phase 3：部署入口统一

- 改造原生安装器输出；
- 新增一行 Docker 安装器；
- 覆盖 systemd、OpenRC、Docker 的全新安装与重复执行；
- 验证重启、升级和数据持久化。

验收：两种部署都只需一条安装命令和浏览器操作，不需要 SSH 隧道或容器内命令。

### Phase 4：发布与恢复状态机瘦身

- 引入统一 desired/applied generation；
- 删除全局 degraded 写锁和失败 Revision 状态；
- 合并 endpoint pending 状态；
- 提供重试、恢复上一个版本和诊断操作；
- 迁移现有数据库并验证掉电/重启场景。

验收：所有注入故障下，要么新配置成功生效，要么旧配置继续工作；面板始终可用于修复。

### Phase 5：核心管理和高级 UI 清理

- 保留并简化 `release`/`alpha`、自动更新、检查周期、手工更新和健康回退；
- 明确 SQLite 用户设置高于 m-ui Release、镜像、TOML 与程序默认值；
- 启动后按持久化策略在后台对齐所选通道，失败保持最后健康核心并继续服务；
- 配置历史、Controller 端点和审计移动到高级区域，核心策略保留为普通系统设置；
- 删除不再使用的 API、表、状态结构、文案和测试。

验收：选择“Alpha + 自动更新”后，连续经历 m-ui 更新、重装、容器重建和主机重启，设置
均不变化，启动后自动运行官方最新 Alpha；默认 UI 不出现内部状态机概念，生产代码和测试
总量仍出现实质性净减少。

### Phase 6：发布与真实部署验收

- 完整执行 Go、前端、race、构建、真实 Mihomo 和 Docker/原生 smoke；
- 从空数据目录测试完整首次使用；
- 从当前正式版数据副本测试原地升级；
- 在真实 Debian/systemd、Alpine/OpenRC 和 Docker 主机验证；
- 验证服务器 IP、HTTPS 反向代理和 SSH 隧道三种访问方式；
- 发布后用最终镜像/包重新走一遍用户路径，而不是只采信 CI。

## 10. 必须新增的端到端测试

- 非回环客户端通过 `SERVER_IP` 完成 setup；
- HTTPS 反向代理下完成 setup；
- 无 token、错误 token、重复 token 和并发 setup；
- 全新 Docker 安装器到二维码输出；
- 全新原生安装器到二维码输出；
- onboarding 任一步失败不留下半成品；
- 配置验证失败不改变数据库或运行 YAML；
- reload/健康检查失败保持最后可用配置，并允许网页重试或修正；
- 服务在 desired/applied 不一致时重启并自动恢复；
- 当前正式版数据库无损升级；
- 容器重建、主机重启和 m-ui 更新后管理员、节点、用户、密钥与分享信息保持不变。
- `release`/`alpha`、自动更新和检查周期在 m-ui 更新、重装、容器重建及主机重启后保持；
- 保存“Alpha + 自动更新”立即触发通道对齐，启动后发现较新 Alpha 自动验证、切换并运行；
- Alpha 下载、校验、重启和健康检查分别失败时保持最后健康核心，设置不丢失且面板可用。

## 11. 完成定义

只有同时满足以下条件，全面改进才算完成：

- 用户无需理解项目内部安全模型即可安全完成首次设置；
- 默认部署文档中的每一步都由真实端到端测试覆盖；
- 首个可用节点在一次向导操作中创建并验证；
- 正常 UI 不暴露 loopback、Controller connect、generation、degraded 或 Revision SHA；
- 可恢复故障不会永久锁死配置写入；
- 安全底线对用户无感，不再增加额外终端、隧道、文件或确认步骤；
- 用户选择的核心通道和自动更新策略是跨 m-ui 生命周期持久化的产品状态；
- 代码库删除的状态、分支、API 和测试多于为简化新增的部分；
- 最终发布产物在真实主机上完成从安装到客户端导入的完整验证。
